# Planning a TabbyAPI `/metrics` endpoint

Research date: 2026-09-25. This records the source-based design research; its proposed contract and implementation sequence below are historical planning notes. The implemented extension is specified by [the version 1 contract](../metrics-contract.md) and covered by the CPU tests in `tests/`. Detailed, pinned upstream inventories are in [vLLM](metrics-vllm.md) (`25b0add7b8a1c944d5c4e364f2de6aa82497a2ad`), [llama.cpp](metrics-llamacpp.md) (`e85e15cf6d810cd1268498c2e5b657bb3ece47bc`), and [SGLang](metrics-sglang.md) (`2f5c9ac43d76eef11e8561c89c55a79db7db715a`). Each report has the full source-line citation set and reproducible read-only checks. The target TabbyAPI pin is `f07131cd8fe34e449fe87cdd3a066b52b96d3cac`.

## What the upstream servers actually do

| Concern | vLLM V1 | llama.cpp `llama-server` | SGLang SRT |
| --- | --- | --- | --- |

These are materially different contracts despite the common route name. vLLM's [route and metric registration](https://github.com/vllm-project/vllm/blob/25b0add7b8a1c944d5c4e364f2de6aa82497a2ad/vllm/entrypoints/serve/instrumentator/metrics.py#L52-L81), llama.cpp's [formatter](https://github.com/ggml-org/llama.cpp/blob/e85e15cf6d810cd1268498c2e5b657bb3ece47bc/tools/server/server-task.cpp#L1517-L1618) and [scrape/reset path](https://github.com/ggml-org/llama.cpp/blob/e85e15cf6d810cd1268498c2e5b657bb3ece47bc/tools/server/server-context.cpp#L4657-L4726), and SGLang's [collector](https://github.com/sgl-project/sglang/blob/2f5c9ac43d76eef11e8561c89c55a79db7db715a/python/sglang/srt/observability/metrics_collector.py#L255) support the comparison. For SGLang, the detailed inventory spans 150 declared core families plus auxiliary HTTP/function/CPU families; it is an inventory of possible families, not a promise that every series appears on an idle server.

### Lessons for our route

1. **Use standard Prometheus exposition, with our own names.** `/metrics` should emit HELP/TYPE/sample lines with a Prometheus content type. A `vllm:` or `sglang:` alias would be misleading because their queue, cache, timing, and token semantics differ. Follow [Prometheus naming and cardinality guidance](https://prometheus.io/docs/practices/naming/).
2. **Do not let scraping change measurements.** llama.cpp's interval throughput gauges reset on GET, so two consumers change each other's view. Use cumulative counters and compute rates from two scrapes; use gauges only for true current state.
3. **Separate live state from completed outcomes.** A brief prefill can begin and finish between scrapes; an active-prefill gauge alone cannot show its work. vLLM and SGLang expose token counters or histograms that survive it. Final-request histograms lag until completion and are not live rates.
4. **Name timing boundaries precisely.** vLLM's engine event intervals and SGLang's tokenizer-manager intervals are not necessarily client-observed wire latency. A Tabby metric based on `time_enqueued + time_prefill` must not be called client TTFT. Use a timestamp at request acceptance and first emitted token for a clearly defined server TTFT, or explicitly name it engine time.
5. **Keep labels bounded and private.** Use fixed state/outcome/source labels and at most a loaded-model identity. No request IDs, IPs, API keys, prompt/output text, user-provided paths, arbitrary error strings, or unbounded client labels. Prometheus warns that each label combination creates a time series.
6. **Treat absent, zero, and stale separately.** Conditional MTP/cache metrics can be absent; an observed zero has a different meaning. Counter resets on restart must be detected by clients; gauges need prompt updates when a job finishes or a model unloads.

## TabbyAPI source reality

The pinned TabbyAPI has no Prometheus dependency or `/metrics` route. Its FastAPI app is constructed in [`endpoints/server.py`](https://github.com/theroyallab/tabbyAPI/blob/f07131cd8fe34e449fe87cdd3a066b52b96d3cac/endpoints/server.py#L18-L101). The ExLlamaV3 backend has observable `started`, `prefill`, streaming, and EOS events and calls `status_display.add_job/remove_job` ([backend event loop](https://github.com/theroyallab/tabbyAPI/blob/f07131cd8fe34e449fe87cdd3a066b52b96d3cac/backends/exllamav3/model.py#L1700-L1848)). The status display tracks queued/prefill/generating and cache statistics even though its visual rendering only runs in a TTY ([status source](https://github.com/theroyallab/tabbyAPI/blob/f07131cd8fe34e449fe87cdd3a066b52b96d3cac/common/status_display.py#L28-L80)). Finished results include queue, prefill, generation time, prompt/cache/generated tokens, and optional draft accepted/rejected tokens ([finish assembly](https://github.com/theroyallab/tabbyAPI/blob/f07131cd8fe34e449fe87cdd3a066b52b96d3cac/backends/exllamav3/model.py#L1438-L1486)).

An earlier, monkeypatch-based prototype obtained these values by wrapping `log_metrics`, `status_display.add_job`, and app setup. It delivered a useful dashboard, but monkeypatching imports obscured the serving identity and tied monitoring to private functions. A new endpoint should use explicit, testable event calls in a small metrics module, preferably contributed upstream. Until upstream accepts it, the local deployment must identify the maintained patch as custom rather than claiming an unmodified TabbyAPI checkout. A sidecar that only polls stock HTTP endpoints cannot recover internal queue, prefill, cache, or MTP data.

## Proposed first contract

The names below are provisional and should be frozen in a spec before implementation. Expose them with `tabbyapi_` prefix, base units, stable HELP text, and bounded labels. Use a single in-process registry for the current single-Uvicorn-process deployment; define a separate multiprocess design if that architecture changes. Make metrics opt-in in TabbyAPI configuration and enabled in this deployment's config. Protect the route using TabbyAPI's existing API-key dependency; with authentication disabled, network reachability is the only access boundary.

| Family | Type and source | Defined meaning |
| --- | --- | --- |
| `tabbyapi_model_loaded` | Gauge, model lifecycle | 1 only when the backend container is loaded, otherwise 0. No path label. |
| `tabbyapi_backend_info{backend="exllamav3"}` | Gauge fixed to 1 while loaded | Actual loaded backend identity from the container, with a bounded backend-name label; absent when unloaded. |
| `tabbyapi_requests_active{state="queued|prefill|decode"}` | Gauge, explicit job transitions | Current jobs in mutually exclusive engine states; removal decrements exactly once on success, cancel, or error. |
| `tabbyapi_requests_total{outcome="completed|cancelled|error"}` | Counter, finalization | One increment per admitted generation job. HTTP rejections before admission are outside this family. |
| `tabbyapi_prompt_tokens_total{source="computed|cached"}` | Counter, final EOS result | Engine processed/reused prompt tokens split using the final raw prompt and cached counts. The pinned `started` and `prefill` events cannot supply this split before EOS. |
| `tabbyapi_generated_tokens_total` | Counter, accepted output progress | New target output tokens, once per token accepted into the response, including a job that later cancels. Do not mix with draft proposals. |
| `tabbyapi_engine_phase_duration_seconds{phase="queue|prefill|decode|total"}` | Histogram, final backend result | Engine-reported phases; total is the sum of those phases, not HTTP end-to-end latency. Published on completed jobs with valid finite timings. |
| `tabbyapi_engine_time_to_first_token_seconds` | Histogram, backend job boundary | Time from generator job admission to its first accepted output token event, for streaming and nonstreaming alike. Excludes request parsing and network delivery; implement only after exact event timestamps are established. |
| `tabbyapi_kv_cache_tokens{state="capacity|used|cached|free"}` | Gauge, backend `get_cache_stats` | Backend-reported logical token capacity/state. Document any overlapping categories; emit no sample while unavailable rather than a false zero. |
| `tabbyapi_mtp_draft_tokens_total{outcome="accepted|rejected"}` | Counter, final result | Draft-token outcomes when MTP/drafting actually reports them. No synthetic zero on unsupported backends. |

GPU VRAM/utilization belongs to the optional `nvidia-smi` collector or a host exporter, not the inference-process route. HTTP status/rejection counters are a separate later concern; `requests_total` above starts only after engine admission. Histograms should use bounded buckets tuned to subsecond first-token times, long prefills, and long generations; they support later p50/p90/p99 calculations without exporting raw request records ([Prometheus histogram guidance](https://prometheus.io/docs/practices/histograms/)). Do not export precomputed percentile gauges or scrape-window throughput gauges.

## Implementation and acceptance sequence

1. **Freeze semantics.** Specify each family's unit, update event, inclusion of aborted work, label values, histogram buckets, model unload behavior, and expected absence. Decide whether metrics include all TabbyAPI endpoints or only EXL3 generation; the first contract above is engine-specific except model state. Define route access in the same spec.
2. **Add the narrow native seam.** Add a metrics registry and explicit backend event calls at admission, stage transitions, output progress, finalization, and model load/unload; register `GET /metrics` through the normal FastAPI app. Avoid wrapping or replacing the startup entrypoint, log function, or status display methods. Make observation failure unable to change generation, but count/log instrumentation failures so missing data is diagnosable.
3. **Focused local verification.** Mock the real backend event sequence and assert exact counter/gauge/histogram values for idle, short prefill, stream/nonstream, coalesced chunks, cache hit, MTP off/on, cancel, exception, model unload, and repeated/concurrent scrapes. Check content type and parseability with the Prometheus parser. Assert no prompts, outputs, IDs, keys, or raw error strings appear; assert no metric changes solely because of a scrape.
4. **Integrate the CLI only after the route passes.** Compute rolling prefill/decode rates from successive counters, preserve absent-vs-zero and stale-age behavior, and derive latency percentiles from histogram bucket deltas with disclosed bucket resolution. Keep the current reduced native monitor until then.
5. **Target validation after explicit host authorization.** Install the patched/pinned candidate in an isolated environment without disrupting the current service; verify process/version identity and a passive scrape. Then run authorized streaming/nonstreaming, small/large prefill, cache-reuse, MTP, cancellation/error, and model unload/reload scenarios. Retain raw exposition snapshots and compare counters to observed generator outputs. Check scrape overhead and that repeated scrapes do not alter throughput or inference.

Open decision: an upstream TabbyAPI PR would eliminate a long-lived local patch if accepted, but it cannot supply live metrics until merged and deployed. The implementation should therefore keep the patch minimal, reviewable, and pinned while clearly identifying the runtime as extended TabbyAPI.
