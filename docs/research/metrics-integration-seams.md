# TabbyAPI metrics integration seams

Research date: 2026-09-25

TabbyAPI pin: `f07131cd8fe34e449fe87cdd3a066b52b96d3cac`

Scope: read-only source inspection of the pinned `tabbyAPI/` submodule. No route was added, no inference was run, and no endpoint or host was contacted.

Correction from the implementation audit: the original notes below describe `started` as carrying cached tokens and propose event-level computed/cached prompt splitting. Pinned ExLlamaV3's `started` event does **not** supply a cached-token count; its cumulative `curr_progress` includes reused KV positions. The implemented [version 1 contract](../metrics-contract.md) records the computed/cached split only from the successful EOS result. The original source-inspection notes are retained below as the research trail, not as the accepted metric semantics.

This note supplements [the metrics comparison and plan](metrics-comparison-and-plan.md). Labels below distinguish **FACT** (visible in the pinned source), **INFERENCE** (recommended interpretation or patch design), and **UNKNOWN** (not established by this checkout).

## Route and authorization

- **FACT:** `setup_app()` builds the FastAPI app and includes the selected OAI/Kobold routers and core router in [`endpoints/server.py`](https://github.com/theroyallab/tabbyAPI/blob/f07131cd8fe34e449fe87cdd3a066b52b96d3cac/endpoints/server.py#L18-L74). Its app-wide dependencies come from `get_global_depends()`, which currently adds request ID assignment and optional request logging, but no API-key check ([`common/networking.py`](https://github.com/theroyallab/tabbyAPI/blob/f07131cd8fe34e449fe87cdd3a066b52b96d3cac/common/networking.py#L245-L252)).
- **FACT:** Existing generation routes attach `Depends(check_api_key)` at the route ([`endpoints/OAI/router.py`](https://github.com/theroyallab/tabbyAPI/blob/f07131cd8fe34e449fe87cdd3a066b52b96d3cac/endpoints/OAI/router.py#L58-L62)); `check_api_key` accepts `x-api-key` or Bearer authorization and permits access when auth is disabled ([`common/auth.py`](https://github.com/theroyallab/tabbyAPI/blob/f07131cd8fe34e449fe87cdd3a066b52b96d3cac/common/auth.py#L219-L242)).
- **INFERENCE:** Register `GET /metrics` from `setup_app()` (or include a dedicated metrics router there), with an explicit auth dependency. The global app dependencies do not protect it. Decide explicitly whether Prometheus scraping uses an API key, a separate network boundary, or a separately configurable policy; upstream examples differ, and this source does not provide a scrape-auth convention.
- **FACT:** `tabbyAPI/pyproject.toml` lists FastAPI and other dependencies but no `prometheus-client` dependency ([dependency list](https://github.com/theroyallab/tabbyAPI/blob/f07131cd8fe34e449fe87cdd3a066b52b96d3cac/pyproject.toml#L13-L45)).
- **UNKNOWN:** The intended exposition library, dependency policy, route opt-in/configuration, and behavior when metrics are disabled have not been decided. Pin source alone cannot establish the eventual text format or content type.

## Generation job lifecycle

- **FACT:** OAI completion and chat routes validate access, obtain the loaded model, create a `DisconnectHandler`, and return either an SSE response or await a non-stream response ([completion route](https://github.com/theroyallab/tabbyAPI/blob/f07131cd8fe34e449fe87cdd3a066b52b96d3cac/endpoints/OAI/router.py#L58-L106); the chat route starts at lines 110 onward). Both paths eventually consume the backend generation iterator.
- **FACT:** `ExllamaV3Container.stream_generate()` records a request in `active_job_ids` after load synchronization and before delegating to `generate_gen`; it removes that record in a `finally` block ([backend lifecycle](https://github.com/theroyallab/tabbyAPI/blob/f07131cd8fe34e449fe87cdd3a066b52b96d3cac/backends/exllamav3/model.py#L1299-L1327)). This outer record uses `None` until the actual `AsyncJob` is constructed, so it also covers the brief setup interval.
- **FACT:** In `generate_gen()`, prompt tokenization, context validation, sampler setup, and request logging precede `AsyncJob` construction. The job is then stored in `active_job_ids`, added to `status_display`, and consumed from its async iterator ([admission seam](https://github.com/theroyallab/tabbyAPI/blob/f07131cd8fe34e449fe87cdd3a066b52b96d3cac/backends/exllamav3/model.py#L1540-L1719)).
- **FACT:** Generator events call `JobStatus.started()` on `stage == "started"`, `prefill()` on `stage == "prefill"`, and `generated()` only when a streaming result has text ([event consumer](https://github.com/theroyallab/tabbyAPI/blob/f07131cd8fe34e449fe87cdd3a066b52b96d3cac/backends/exllamav3/model.py#L1720-L1795)). At the pinned ExLlamaV3 revision `958ec933361b24eb8426ec7222e5b0062a679dcd`, job prefill events set `curr_progress` from the sum of each sequence's `kv_position` ([job.py](https://github.com/turboderp-org/exllamav3/blob/958ec933361b24eb8426ec7222e5b0062a679dcd/exllamav3/generator/job.py#L1468-L1479)); the generator event contract describes it as prompt tokens ingested so far ([generator.py](https://github.com/turboderp-org/exllamav3/blob/958ec933361b24eb8426ec7222e5b0062a679dcd/exllamav3/generator/generator.py#L459-L468)). `JobStatus` tracks queued/prefill/generating and token progress in memory; `StatusDisplay.remove_job()` increments a generic completed count for every removal, including non-success removal ([status tracker](https://github.com/theroyallab/tabbyAPI/blob/f07131cd8fe34e449fe87cdd3a066b52b96d3cac/common/status_display.py#L30-L69), [registration/removal](https://github.com/theroyallab/tabbyAPI/blob/f07131cd8fe34e449fe87cdd3a066b52b96d3cac/common/status_display.py#L193-L204)).
- **FACT:** Streaming events can be coalesced by draining `job.queue` and merging several streaming dictionaries before accounting/yielding the merged result ([coalescing logic](https://github.com/theroyallab/tabbyAPI/blob/f07131cd8fe34e449fe87cdd3a066b52b96d3cac/backends/exllamav3/model.py#L1731-L1753)). The consumer increments its local generated-token total from the merged chunk's token IDs before yielding ([token accounting](https://github.com/theroyallab/tabbyAPI/blob/f07131cd8fe34e449fe87cdd3a066b52b96d3cac/backends/exllamav3/model.py#L1754-L1794)).
- **INFERENCE:** `curr_progress` is an absolute prompt position, not a per-event delta: the producer emits summed `kv_position`, and the generator contract explicitly defines the field as prompt tokens ingested so far. For counters, retain a per-job previous position and add only positive deltas; for cumulative prompt totals, reconcile to the EOS result. The `started` event separately reports cached tokens, so validate that relationship before dividing progress into disjoint computed and cached token counters. Keep the prefill gauge's update as an absolute value (consistent with `JobStatus.prefill()` taking a max), not by summing progress samples.
- **INFERENCE:** Queue gauge admission can begin at `stream_generate()`'s `active_job_ids[request_id] = None` if setup time should count as queued. If the product contract defines admission only once ExLlama `AsyncJob` exists, use `generate_gen()` job creation instead. That boundary must be named and tested; current code does not call the first of these engine-queue admission.
- **UNKNOWN:** This backend seam does not represent every endpoint as an inference request: embeddings use a separate container/backend. A first release must state whether its request families are EXL3 generation-only or cover all API work.

## Stage, token, timing, and outcome data

- **FACT:** Final EOS results contain `prompt_tokens`, `cached_tokens`, `time_prefill`, `new_tokens`, `time_generate`, `time_enqueued`, and optional `accepted_draft_tokens` / `rejected_draft_tokens`; ExLlamaV3 increments `new_tokens` when it accepts a sampled token and reports cumulative request tokens on EOS ([job token/EOS accounting](https://github.com/turboderp-org/exllamav3/blob/958ec933361b24eb8426ec7222e5b0062a679dcd/exllamav3/generator/job.py#L627-L640), [EOS result fields](https://github.com/turboderp-org/exllamav3/blob/958ec933361b24eb8426ec7222e5b0062a679dcd/exllamav3/generator/job.py#L757-L783)). `handle_finish_chunk()` rounds several timing/count values for the API finish object and computes `total_time = queue + prefill + generation` ([finish assembly](https://github.com/theroyallab/tabbyAPI/blob/f07131cd8fe34e449fe87cdd3a066b52b96d3cac/backends/exllamav3/model.py#L1410-L1487)). The unrounded engine result is available before it assembles that API object.
- **FACT:** `generate_gen()` captures the finish object only for an EOS result, yields it, and then breaks. Its cancellation branch cancels the engine job; other exceptions go through `_recover_from_generation_error()` and propagate; its `finally` removes the status entry. `log_metrics()` runs only when an EOS finish object was saved ([terminal and cleanup branches](https://github.com/theroyallab/tabbyAPI/blob/f07131cd8fe34e449fe87cdd3a066b52b96d3cac/backends/exllamav3/model.py#L1796-L1845)).
- **INFERENCE:** Use the raw EOS result, before API rounding, for final histograms and token counters when counting final totals. If generated-token counters should reflect output before EOS (including cancellations), increment only from token IDs in the streaming-consumer path and ensure coalesced spans count each ID once. A separate outcome finalizer must classify EOS as completed, `CancelledError` as cancelled, and propagated exceptions as error exactly once; `status_display.completed` is not a success counter.
- **FACT:** The pinned ExLlamaV3 job initializes its enqueue timestamp when created, marks the first prefill time at prefill entry, and accumulates `time_enqueued = first_prefill - enqueue`, `time_prefill = first_token - first_prefill`, and `time_generate = last_token - first_token` on EOS/requeue ([job timestamps and phase equations](https://github.com/turboderp-org/exllamav3/blob/958ec933361b24eb8426ec7222e5b0062a679dcd/exllamav3/generator/job.py#L757-L778), [enqueue timestamp](https://github.com/turboderp-org/exllamav3/blob/958ec933361b24eb8426ec7222e5b0062a679dcd/exllamav3/generator/job.py#L1173-L1176), [prefill timestamp](https://github.com/turboderp-org/exllamav3/blob/958ec933361b24eb8426ec7222e5b0062a679dcd/exllamav3/generator/job.py#L1203-L1215)). The first token timestamp is set in generator decode paths ([generator first-token sites](https://github.com/turboderp-org/exllamav3/blob/958ec933361b24eb8426ec7222e5b0062a679dcd/exllamav3/generator/generator.py#L640-L647)). These are engine timings; they exclude request parsing and network delivery and must not be named client end-to-end latency. The engine first-token point is distinct from Tabby's first nonempty emitted text.
- **FACT:** In ExLlamaV3 prefill, cache-matched prefix tokens advance `seq.kv_position`, increment `cached_tokens`, and count toward progress before uncached prompt forward passes ([cache-match path](https://github.com/turboderp-org/exllamav3/blob/958ec933361b24eb8426ec7222e5b0062a679dcd/exllamav3/generator/job.py#L1289-L1304)). EOS `cached_tokens` is derived from matched cached pages and partial cached tokens ([EOS cache fields](https://github.com/turboderp-org/exllamav3/blob/958ec933361b24eb8426ec7222e5b0062a679dcd/exllamav3/generator/job.py#L763-L778)). Thus `curr_progress` includes cached prompt positions; subtracting cached tokens from progress is needed to estimate newly computed prompt tokens. **UNKNOWN:** Event-level validation is still required for partial prefill, multimodal inputs, requeued jobs, and whether Tabby's encoded `context_len` always matches ExLlama's EOS prompt-token definition.
- **UNKNOWN:** `generate_gen()` catches `asyncio.CancelledError`, but cancellation may also occur outside this consumer (for example request handling or generator teardown). Outcome accounting needs tests that cover cancellation at each async boundary and prove finalization is idempotent.

## Model and cache lifecycle

- **FACT:** `common.model.container` is the global container. During load, a new container is assigned globally only after its load generator finishes; the backend sets `self.loaded = True` after generator creation and warmup ([load path](https://github.com/theroyallab/tabbyAPI/blob/f07131cd8fe34e449fe87cdd3a066b52b96d3cac/common/model.py#L148-L240), [loaded transition](https://github.com/theroyallab/tabbyAPI/blob/f07131cd8fe34e449fe87cdd3a066b52b96d3cac/backends/exllamav3/model.py#L831-L863)).
- **FACT:** `common.model.unload_model()` awaits the current container's unload and then clears the global reference ([global unload](https://github.com/theroyallab/tabbyAPI/blob/f07131cd8fe34e449fe87cdd3a066b52b96d3cac/common/model.py#L140-L146)). `ExllamaV3Container.unload()` waits/cancels jobs, releases model/cache/generator objects, and logs completion ([backend unload](https://github.com/theroyallab/tabbyAPI/blob/f07131cd8fe34e449fe87cdd3a066b52b96d3cac/backends/exllamav3/model.py#L1051-L1108)).
- **INFERENCE:** Tie `model_loaded` and loaded-model identity to the global-container lifecycle. Emit the transition only after successful global assignment and after the unload has completed / global container is cleared. Do not put a filesystem path or arbitrary model identifier in a label; a single bounded identity info gauge or no model label avoids path privacy and cardinality problems.
- **FACT:** `StatusDisplay._cache_stats()` finds `container.generator.generator.get_cache_stats()` and returns `None` when unavailable or when the call raises. The display reads `max_tokens`, `used_tokens`, `cached_tokens`, `pending_jobs`, hit rates, and optional system-memory tier values ([cache read and use](https://github.com/theroyallab/tabbyAPI/blob/f07131cd8fe34e449fe87cdd3a066b52b96d3cac/common/status_display.py#L208-L258)). The pinned ExLlamaV3 method documents occupancy, capacity, reusable cache, allocation and hit-rate fields; its reusable page-chain walk is memoized by a page-table signature and repeated calls between changes are described as cheap ([get_cache_stats contract and memoization](https://github.com/turboderp-org/exllamav3/blob/958ec933361b24eb8426ec7222e5b0062a679dcd/exllamav3/generator/generator.py#L275-L320)).
- **INFERENCE:** A metrics scrape should represent unsupported/unavailable cache stats as absent and must not turn `None` into zero. Calling this method for scrape-time reads has a clear intended use and memoizes the expensive chain walk; still validate that concurrent reads are safe and consider the per-call page-table signature work, especially for large caches. Alternatively refresh a snapshot from an explicit safe polling task.
- **UNKNOWN:** The ExLlamaV3 source documents display use and memoizes cache-chain traversal, but does not establish synchronization guarantees for calling `get_cache_stats()` concurrently with generator mutation. The runtime contract is pinned to ExLlamaV3 `958ec933361b24eb8426ec7222e5b0062a679dcd`; compatibility with a different installed wheel remains unverified.

## Recommended patch points

1. Add a small `common.metrics` module with one process-local registry and explicit methods for model transitions, request admission/stage changes, cumulative token progress, final outcomes, timings, and cache snapshot. Define all units, buckets, bounded label values, cancellation semantics, and missing-data semantics before naming families.
2. Register a dedicated `GET /metrics` route in `endpoints/server.py` with explicit auth policy. Return Prometheus text exposition and content type via a supported library or a deliberately maintained formatter; the current dependency set contains no Prometheus client.
3. Add metric event calls to `common.model` around successful global load assignment and global unload completion; to `ExllamaV3Container.stream_generate()` / `generate_gen()` around admission, engine event changes, token progress, and exactly-once terminal outcome. Avoid wrapping log functions or patching status display methods.
4. Keep cache collection on an availability-aware path; validate direct scrape reads before adopting them. Keep labels to fixed state/outcome/phase/source/backend values and a controlled model identity policy. Never export request IDs, prompts, outputs, API keys, IPs, model paths, or raw exception text.
