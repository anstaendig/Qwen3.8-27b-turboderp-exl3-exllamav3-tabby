# TabbyAPI Prometheus `/metrics` contract, version 1

Status: implementation contract for this project's pinned TabbyAPI `f07131cd8fe34e449fe87cdd3a066b52b96d3cac` and ExLlamaV3 backend. The target is an independently useful server metric API; a monitor is merely one possible consumer. The existing [source comparison](research/metrics-comparison-and-plan.md) records the pinned vLLM and SGLang references.

## Scope and evidence

**Source facts.** Pinned TabbyAPI creates a FastAPI app without `/metrics` ([app setup](https://github.com/theroyallab/tabbyAPI/blob/f07131cd8fe34e449fe87cdd3a066b52b96d3cac/endpoints/server.py#L18-L101)). Its EXL3 generation loop admits a job, observes `started`, `prefill`, streaming chunks and EOS, and removes the job in `finally` ([generation loop](https://github.com/theroyallab/tabbyAPI/blob/f07131cd8fe34e449fe87cdd3a066b52b96d3cac/backends/exllamav3/model.py#L1700-L1858)). In pinned ExLlamaV3 `958ec933361b24eb8426ec7222e5b0062a679dcd`, `started` has no `cached_tokens`; `curr_progress` is a cumulative KV position that includes reused prefix pages, while the exact cached count arrives with EOS ([started event](https://github.com/turboderp-org/exllamav3/blob/958ec933361b24eb8426ec7222e5b0062a679dcd/exllamav3/generator/generator.py#L1434-L1444), [progress event](https://github.com/turboderp-org/exllamav3/blob/958ec933361b24eb8426ec7222e5b0062a679dcd/exllamav3/generator/job.py#L1469-L1476), [EOS fields](https://github.com/turboderp-org/exllamav3/blob/958ec933361b24eb8426ec7222e5b0062a679dcd/exllamav3/generator/job.py#L762-L779)). The finish result provides raw `time_enqueued`, `time_prefill`, `time_generate`, prompt/cached/new token counts, and optional draft accepted/rejected counts, although the current presentation code rounds some values ([finish assembly](https://github.com/theroyallab/tabbyAPI/blob/f07131cd8fe34e449fe87cdd3a066b52b96d3cac/backends/exllamav3/model.py#L1438-L1492)). The generator exposes `get_cache_stats()` with `max_tokens`, `used_tokens`, and `cached_tokens` to the status display; the display's state machine is separate from whether the TTY display is active ([status source](https://github.com/theroyallab/tabbyAPI/blob/f07131cd8fe34e449fe87cdd3a066b52b96d3cac/common/status_display.py#L28-L80), [cache reading](https://github.com/theroyallab/tabbyAPI/blob/f07131cd8fe34e449fe87cdd3a066b52b96d3cac/common/status_display.py#L209-L252)).

**Design decisions.** Follow [Prometheus metric naming](https://prometheus.io/docs/practices/naming/): application prefix, seconds for durations, `_total` for counters, bounded labels. Expose Prometheus text with `# HELP`, `# TYPE`, and the installed client's matching `Content-Type`, using a standard client registry; see the [exposition format](https://prometheus.io/docs/instrumenting/exposition_formats/). The pinned `prometheus-client==0.26.0` advertises `text/plain; version=1.0.0; charset=utf-8`; that value was checked in the lightweight local test environment. Use classic histograms with fixed inclusive buckets and `_bucket`, `_sum`, `_count` samples ([histogram semantics](https://prometheus.io/docs/practices/histograms/)). vLLM motivates separate state, work and timing measurements; SGLang motivates explicit phase and cache meanings. Neither project's metric names or estimates are aliases for ours.

**Unknown until implementation/live validation.** Whether every engine callback arrives for cancellation, cache-stat collection cost under the target model, and runtime precision of engine timing values require local event-sequence tests and an authorized live check. Do not infer GPU usage, network delivery time or individual benchmark request identity from this endpoint.

## Endpoint and lifecycle

`GET /metrics` returns UTF-8 Prometheus text, HTTP 200 and the pinned client's `Content-Type: text/plain; version=1.0.0; charset=utf-8` (equivalent valid parameter ordering is fine). It is read-only and must not reset counters, windows, histograms or gauges. Repeated and concurrent GETs of unchanged server state have equivalent samples. Each sample is nonnegative and finite. A failed collection omits the affected optional gauge family; it does not publish a false zero or abort generation. The server must not cache an old scrape after a collection failure.

The registry lives for one serving process. Counters and histograms begin at zero and reset only on process restart; model unload does not reset historical totals. A multiworker server needs its own aggregation and reset design before this contract applies. Scrape clients detect restart through ordinary counter-reset handling and target health. Scrape cadence never defines a metric's update cadence.

The route uses TabbyAPI's existing `check_api_key` dependency when authentication is enabled ([auth check](https://github.com/theroyallab/tabbyAPI/blob/f07131cd8fe34e449fe87cdd3a066b52b96d3cac/common/auth.py#L219-L243)); the app's global dependencies do not themselves require a key ([global dependencies](https://github.com/theroyallab/tabbyAPI/blob/f07131cd8fe34e449fe87cdd3a066b52b96d3cac/common/networking.py#L245-L254)). This project's `config.yml` enables authentication and binds `127.0.0.1` by default; if authentication is disabled, network reachability becomes the only access boundary. No query-string key, identity-bearing label, prompt, output, or raw exception is part of exposition. Enabling the route through new configuration requires a field verified against the pinned `common/config_models.py`, or an explicit maintained patch adding that field.

## Metric families

All metrics below cover EXL3 text-generation jobs admitted immediately after successful `AsyncJob` construction, which synchronously enqueues the engine job in pinned ExLlamaV3 ([constructor](https://github.com/turboderp-org/exllamav3/blob/958ec933361b24eb8426ec7222e5b0062a679dcd/exllamav3/generator/async_generator.py#L123-L132)). This is before any subsequent await or display registration. Streaming and nonstreaming API routes share that boundary. One HTTP request can produce multiple jobs or fail before admission, so `requests_total` means **engine jobs**, not HTTP requests. An idle process publishes fixed state gauges and initialized zero counters/histograms; optional cache and MTP families can be absent. No model, endpoint, client, request or user label appears in version 1.

| Family | Type; labels | Observation and unit |
| --- | --- | --- |
| `tabbyapi_metrics_schema_info` | Gauge; `version="1"` | Always 1 while the endpoint is available. Identifies the public contract, not the server build. |
| `tabbyapi_model_loaded` | Gauge; none | 1 while the globally committed EXL3 model container is loaded, else 0. Read current state on scrape; no model path or user supplied model name. |
| `tabbyapi_requests_active` | Gauge; `state="queued|prefill|decode"` | Current admitted engine jobs. Exactly one state per active job; initialized children are 0. |
| `tabbyapi_requests_total` | Counter; `outcome="completed|cancelled|error"` | Increment once on job finalization. These values are mutually exclusive. `completed` means an EOS result reached the backend consumer; it is not an HTTP delivery acknowledgment. |
| `tabbyapi_prompt_tokens_total` | Counter; `source="computed|cached"` | On successful EOS, `computed` adds `prompt_tokens - cached_tokens` and `cached` adds the raw final cached-token count. Unit: tokens. No pre-EOS increments or cancel/error estimates because the progress event does not reveal the split. |
| `tabbyapi_output_tokens_total` | Counter; none | Token IDs on nonempty output chunks accepted by the TabbyAPI generation consumer, including output before a later cancellation. Unit: tokens. It does not include draft proposals, hidden/stop tokens or text retokenized merely for display. |
| `tabbyapi_engine_time_to_first_token_seconds` | Histogram; none | Engine job admission to first accepted nonempty output chunk. Observe once at first output, even if the job later cancels or errors. No sample for a job without output. This is server-side time, not client wire TTFT. |
| `tabbyapi_engine_phase_duration_seconds` | Histogram; `phase="queue|prefill|decode|total"` | Observe each valid phase once on successful EOS from the **unrounded** engine result. Queue=`time_enqueued`; prefill=`time_prefill`; decode=`time_generate`; total=sum of all three. These are engine-accounted intervals, not HTTP end-to-end time. |
| `tabbyapi_kv_cache_capacity_tokens` | Gauge; none | `max_tokens` from a valid EXL3 `get_cache_stats()` result. Unit: logical cache tokens. |
| `tabbyapi_kv_cache_used_tokens` | Gauge; none | `used_tokens` from the same result. Unit: logical cache tokens. |
| `tabbyapi_kv_cache_reusable_tokens` | Gauge; none | `cached_tokens` from the same result. This can overlap `used_tokens`; do not add the two. Unit: logical cache tokens. |
| `tabbyapi_mtp_draft_tokens_total` | Counter; `outcome="accepted|rejected"` | On EOS, add engine-reported `accepted_draft_tokens` and `rejected_draft_tokens` only if both are present and valid. Unit: draft tokens. No inferred proposal count for interrupted jobs. |
| `tabbyapi_metrics_observation_errors_total` | Counter; none | Invalid or failed event observations inside the instrumentation path. Excludes cache-scrape failures, which cause omission of the cache gauges. Contains no exception text or request identity. |

Initialization, collection and event rules:

1. Register the fixed `state`, `outcome`, `source`, and `phase` label values at process startup. Register the MTP outcome children on the first successful MTP-enabled backend load; once registered, they remain for the process lifetime across model unloads. A numeric zero then means observed no work since registration. Before an MTP-enabled load, omit the MTP family entirely.
2. Admit a job exactly once as `queued`; `started` moves it to `prefill`; its first output chunk moves it to `decode`. An EOS without text still finalizes correctly. A skipped state is allowed, but decrement only the current state. On cancellation/error/EOS, remove the job and decrement exactly once, including exceptional exits. The three gauges must never become negative.
3. `started` and `prefill` may change only the active-state gauge. They must not increment source-split prompt counters: `started` lacks a cached-token count, and `curr_progress` includes cached KV position. On successful EOS, require valid finite nonnegative `prompt_tokens` and `cached_tokens <= prompt_tokens`; increment `cached` by the latter and `computed` by their difference exactly once. A cancelled or errored job contributes no source-split prompt sample. This completion-only scope must remain explicit for benchmark consumers; a later live-work metric needs its own name and semantics.
4. Count output from each raw source chunk's token ID sequence after its coalesced result is accepted by the consumer. Inspect raw chunks separately so one missing-ID span does not hide known IDs in adjacent spans. The current fallback that tokenizes text when IDs are unavailable is an estimate and must not enter this counter; skip that span and record a bounded instrumentation diagnostic. This makes the counter an exact observation of known IDs rather than a guess.
5. `completed` requires EOS; `cancelled` covers explicit job cancellation or client disconnect detected by the consumer; other exception exits are `error`. Classify once in `finally`. Do not classify requests rejected before engine admission. The completion count must not rely on the console display's `completed` field, which counts removals regardless of outcome.
6. Cache gauges are read from one valid `get_cache_stats()` snapshot on collection, never from configured `cache_size`. The route collects on the serving asyncio loop, which also runs ExLlamaV3's synchronous generator iteration ([pinned async wrapper](https://github.com/turboderp-org/exllamav3/blob/958ec933361b24eb8426ec7222e5b0062a679dcd/exllamav3/generator/async_generator.py#L23-L44)); do not move collection to FastAPI's worker thread without synchronization. Publish all three together only while the model is loaded and all three values are valid. Omit them on unload/unsupported/error. A successful snapshot containing zero is a measured zero. Measure collection cost during host acceptance because the page-chain walk can block the event loop.
7. Engine timings and draft totals are completion-only because their authoritative fields arrive on EOS. Validate each related group together: the computed/cached prompt pair, all four phase observations, and the accepted/rejected draft pair. Reject a malformed group without publishing part of that group; other valid groups can still be recorded. Never replace missing phases with zero. Instrumentation failures must not change generation behavior. Increment the label-free observation-error counter for rejected event observations; never include exception text.

The TTFT bucket upper bounds in seconds are `0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10, 30, 60, 120, 300, +Inf`. The phase-duration bucket bounds in seconds are `0.001, 0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10, 30, 60, 120, 300, 600, 1200, 3600, +Inf`. Buckets are inclusive and cumulative. Boundaries are part of version 1 compatibility; histograms retain all-time distributions since process start. Consumers derive rates from counters and population percentiles from bucket rates, with bucket-resolution limits.

## Consumer and compatibility rules

The endpoint gives aggregate, process-scoped evidence. Benchmark tools can correlate their own run windows with counter increases and histogram distributions, while retaining their own per-request IDs, exact client TTFT, output timings and results. Concurrent unrelated traffic contaminates a benchmark window; `/metrics` alone cannot attribute traffic to a particular benchmark. A failed scrape is missing data. A known zero sample is zero; an absent optional metric is unsupported or unavailable; a stale sample is a consumer-side freshness condition. Consumers should never coerce these into one another.

The public family names, label keys and value sets, units, event boundaries and bucket boundaries form version 1. Additive families are allowed. A semantic change to an existing family requires a new name or a versioned contract; a family must not quietly change from engine time to client time, or from emitted tokens to backend `new_tokens`. The `tabbyapi_metrics_schema_info` value changes only with a documented incompatible contract revision. A model switch within the process leaves historical counters intact; the contract intentionally does not partition them by model. Deployments needing separate model attribution should use separate scrape targets and target labels, not request-controlled series.

Private or unbounded labels are forbidden: prompt/output text, token strings, request ID, API key, IP, model file path, arbitrary model name, error message, URL, user agent and client-supplied metadata. GPU/VRAM/device metrics belong to host exporters. Precomputed p50/p99, scrape-window throughput, and a sum of cache-used plus cache-reusable tokens are outside this contract.
